# 前端联调与演示收口设计方案

## 需求来源

- `需求分析文档.pdf`: 患者端需要登录注册、预约挂号、查看病历、费用支付、留言、AI 智能检索；后台端需要用户、科室、病历、医嘱、处方、检查、住院、归档、费用、系统、AI 等管理能力。
- `概要设计文档.pdf`: 前端使用 Vue 3、Vue Router、Element Plus、Axios，分为患者端 `emr-frontend` 和后台管理端 `manage_code`。

## 当前状态

两个前端项目已经存在基础 API 文件、路由文件、会话恢复和 401/403 处理。多数 `views` 目录还是 `.gitkeep`，页面未完整实现。后端部分接口已经从内存切到数据库，部分接口后续还会继续改造。

## 设计目标

在后端剩余功能持久化完成后，把患者端和后台端页面补成可答辩演示的闭环。前端不做复杂业务计算，只负责表单、列表、状态展示和调用后端 API。

## 交互设计原则

- 后台端采用密集、清晰、可扫描的管理界面，优先表格、筛选、抽屉或弹窗表单。
- 患者端采用简单卡片和步骤式表单，降低操作复杂度。
- 所有列表统一支持分页，默认每页 10 条，对齐非功能需求 `NFR-PERF-04`。
- 所有写操作成功后刷新当前列表，并给出明确成功提示。
- 401/403 继续使用当前 session 事件机制跳转登录或提示无权限。
- 表单字段尽量沿用后端 API 命名，避免额外转换层。

## API 联调顺序

1. 患者端登录、注册、预约、病历、费用。
2. 后台端用户、科室、医生、患者。
3. 后台端病历、模板、归档。
4. 后台端医嘱、处方、检查、工作流。
5. 后台端分诊、入院、出院、费用。
6. 系统内容和 AI 页面。

## 兼容性

- 两个前端继续使用当前 `utils/request.js` 和 `utils/session.js`。
- API baseURL 继续通过环境变量配置，默认走网关 `/cl584734139` 前缀。
- 不要求一次性接入所有复杂图表；仪表盘只做简洁统计和快捷入口。
- 如果后端某服务还未改完数据库版，页面仍可先按接口调用，后端完成后无需改页面路径。

## 验证方式

- 使用 Node 对修改的 JS/Vue 文件做语法检查。
- 安装依赖后分别运行 `npm run build`。
- 使用浏览器手工验证患者端和后台端的核心演示路径。
- 最终演示路径：患者注册登录 -> 预约挂号 -> 医生录入病历 -> 主任审核医嘱/归档 -> 护士执行医嘱 -> 录入费用 -> 患者查看并支付。
