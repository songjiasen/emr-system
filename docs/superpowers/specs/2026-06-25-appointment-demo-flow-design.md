# 患者预约挂号完整演示流程设计

## 背景

测试流程要求从患者预约挂号开始，串起医生确认预约、医生写病历、医嘱审核执行、处方查看、检查申请审核、患者支付检查费用、医生填写检查结果。当前系统已有大部分诊疗链路，但预约确认和检查费用支付状态衔接不完整。

## 目标

- 患者提交预约后，预约状态为 `pending`，页面展示为“待确认”。
- 医生在后台预约管理中确认本人预约，状态变为 `confirmed`。
- 医生基于已确认预约新增病历。
- 医生新增医嘱后为 `pending_audit`，主任审核通过变为 `approved`，护士执行后变为 `executed`。
- 医生新增处方后，患者端可查看处方记录。
- 医生新增检查申请后为 `pending_audit`，主任审核通过变为 `approved`。
- 患者端点击“去检查”后自动生成 100 元检查费用，并跳转到费用支付页；支付成功后检查申请变为 `paid`。
- 医生填写检查结果并保存后，检查申请变为 `finished`，患者端能看到结果。

## 非目标

- 不新增数据库表。
- 不新增 Laravel/Spring migration。
- 不引入真实第三方支付。
- 不改现有登录账号、角色模型和网关前缀。
- 不把检查收费金额做成复杂配置，本次固定为 100 元，满足演示流程。

## 状态口径

### 预约

```text
pending 待确认
  -> confirmed 已确认
  -> cancelled 已取消
```

仅医生可确认自己的预约；患者和管理员仍保留原有查询、取消能力。

### 检查申请

```text
pending_audit 待审核
  -> approved 已通过/待检查
  -> paid 已支付/待填写结果
  -> finished 已完成
```

患者点击“去检查”只生成未支付费用，不直接把检查改为 `paid`。费用支付成功后，患者端调用检查支付确认接口回写 `paid`。

## 兼容性

- 旧预约仍保留 `pending`、`cancelled`；新增 `confirmed` 只影响医生确认后的展示和筛选。
- 旧检查申请如果已经是 `paid`，医生仍可填写结果并保存为 `finished`。
- 现有 `approved` 检查申请仍可点击“去检查”生成费用。
- 不需要数据迁移；如果已有重复检查费用，本次前端会优先复用同一 `businessType=test_request`、`businessId=检查ID` 的未支付费用，减少重复创建。

## 改动范围

- 后端预约服务：新增确认预约接口和服务方法。
- 患者端：调整“去检查”和“支付费用”的联动逻辑，补充检查结果展示。
- 后台端：预约管理增加确认按钮；检查申请增加“填写结果”入口。
- 测试：补预约确认接口测试、检查支付状态测试、前端构建验证。
